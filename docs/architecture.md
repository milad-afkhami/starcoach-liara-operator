# Architecture and evidence boundaries

The React interface talks to one local FastAPI operator. Signed HttpOnly owner sessions partition watches, incidents, evidence and approvals. Mutation routes require the exact configured Origin. Private responses are not cached. The Liara bearer token stays in the operator process; fixtures have no mutation capability.

The owner registry declares HTTP origins/paths and explicit dependency relationships. Inventory itself comes from the provider and requires no source artifact or healthy baseline. Probes resolve once and connect to the approved IP with the original Host/TLS identity, reject redirects/private destinations in live mode, cap bodies at4KiB and preserve sanitized payloads, request IDs and acquisition times. HTTP failure, no endpoint, missing telemetry and observer authentication failures are distinct states.

SQLite stores immutable evidence and bounded observation sessions. Each incident has an append-only observation sequence and a separate material generation. Repeated equivalent failures advance observation history without invalidating an ongoing investigation; release/fingerprint/recovery changes invalidate old conclusions. Run IDs prevent a canceled or superseded model result from overwriting later work. Restart stops old watches and records unfinished investigations as interrupted.

The investigator receives only evidence available by its cutoff, a registered read menu and a typed result schema. It may request a discriminating read, cite supporting/contrary evidence and propose an enrolled repair candidate. It cannot execute cloud operations. Codex runs in a disposable container with separate filesystem mounts and global queue/quota controls. The domain layer validates citations, targets, freshness and allowed outcomes independently of model text. Observer401forces no application change; unsupported/stale evidence may end unresolved.

The trusted operation executor persists the exact source intent before a write, freezes hash-verified bytes, checks current target/release/incident/policy, and writes once. A separate setup ledger creates only two explicitly named disposable demo apps. Initial deployment and baseline enrollment are separate: packaging is not healthy proof. The independent fault controller has its own archive/state and is never imported by the operator or registered as a model tool.

Repair verification separately checks provider readiness, current/serving release identities, expected artifact build IDs, fresh echoed request IDs and the original configured symptom. Three complete success rounds at least five seconds apart must fit a60-second/12-probe budget. Reconciliation may continue for at most10 minutes after a submitted write even if periodic watching expires. Restart during verification is inconclusive rather than a new unbounded attempt. Unknown write outcomes continue holding the target against another writer.

Limitations: the declared service map is not automatic topology discovery; provider schemas and metric units need account-specific live acceptance; HTTP observations describe this operator’s vantage point; source redeployment is not native rollback; process health alone cannot establish customer-task health. The operator is deliberately local for personal model authentication. Production hosting, multi-user identity, alert delivery and an observability database are outside this MVP.
