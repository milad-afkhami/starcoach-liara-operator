# Liara capability evidence

Public contracts were checked22October2026 against [official API introduction](https://docs.liara.ir/references/api/about/), [PaaS OpenAPI](https://developers.liara.ir/spec/paas.yaml), and official CLI commit14ec35f79d703a09a5e3abbb22ba59239cdde80d. The original public-contract investigation is now supplemented by authenticated checks on the exact disposable cloud targets, recorded below.

The adapter scopes every request to explicit `teamID`, uses Bearer authentication, checks name/ID against discovered targets, and strips environment/author/node data. Existing failing and endpoint-less services require no baseline, semantic contract or deployment artifact. Unknown HTTP coverage is not failure. API401/403 means observer access failed; it does not mean the application failed.

Read routes: `/v1/projects`, `/v1/projects/{name}`, `/applets`, `/releases?page=1&count=10`, `/events?start=...&end=...`, `/metrics/summary` and `/metrics/{cpu,memory}?since=...`. Log schemas are deliberately separate: public v1 arrays with datetime/type/message, and current CLI v2 data groups with metaData.releaseId and nanosecond/string pairs. The configurable version defaults to the current CLI route and actual v2 groups have been validated on the disposable account targets; `last_lines` is a boolean, with the local500-line cap enforced separately. No fallback silently reinterprets a payload.

Reads are limited to512KiB, five-second per-network-phase timeouts and one bounded retry for transient failures. Logs ask for a five-minute window and retain at most500 lines, with truncation/empty/stale/future-data quality. CPU/RAM summary normalization now accepts only the exact `cpuUsage`/`memoryUsage` per-applet timestamp/value schema used by the inspected public console. That console renders CPU ratio×100 as percent and memory in bytes; source URL/hash are carried with normalized evidence. Unknown shapes remain unit-unverified; empty, malformed, stale and future samples cannot silently become current zero/healthy readings. A snapshot does not establish sustained saturation or workload capacity, and no exhaustion alert or resize is derived from it. Safe returned data is redacted before persistence/model use. These limits do not establish full log coverage or production observability.

The write adapter now implements scoped source upload/new release and explicit new-app creation. Exact new-app/source/release operations have also been exercised against the actual provider within the recorded scope. Setup and repair require separate exact approvals and no generic POST retry; an ambiguous response stays unknown. Current official CLI creation additionally binds bundlePlanID and network; live account catalogue/network reads discover exact IDs. Native rollback, Kubernetes/tracing access, environment replacement and automatic topology discovery are not claimed. See [deployment preparation](deployment.md) for the inspected tax-inclusive quote and actual setup gate.

Authenticated account compatibility is now being checked on owner-approved disposable targets. Inventory, project, release, metrics-summary and network-event routes have returned actual responses; the initial delivery target serves its packaged build. The deployment and live-acceptance records own exact baseline, fault, repair and remaining delivery results.

The authenticated owner API exposes `POST /api/setup/recommendation`: validated explicit minimum RAM/CPU/disk requirements are matched against a freshly read account catalogue. It produces read-only initial deployment/domain guidance; unavailable/no-matching catalogue states never invent prices. It does not create an app, change a plan or bypass the separate owner setup approval ledger. Incident detail adds fixed evidence-linked remediation guidance only for a current completed diagnosis; model output and deployment approval contracts remain unchanged.

## Network-runtime serving identity

Current network-backed apps do not expose the legacy applet view in the official console; the actual legacy route returned500 after deployment. Their documented lifecycle-event interface returns `data[]` with container ID, action, UNIX-second time and exact release ID. Live reads established integer query parameters and a start-inclusive/end-exclusive interval. The compatibility reader does not fabricate applet snapshots or copy `currentRelease` into a serving identity.

For a newly created network target, it reads a fresh project creation anchor/scale and backfills lifecycle history to an empty older interval. Boundary-second reads must fit strictly below an already observed page-size lower bound, preventing an unseen same-second page from being treated as complete. This relies on stable provider page capacity across interval reads; the returned coverage identifies that boundary check. Unsupported intervals/pagination, explicit truncation, missing creation/history, unknown actions, ambiguous noncommuting order, unknown active releases and scale mismatch remain unknown. Limits are24hours since creation,200events,12GETs and a10-second reader budget; exceeding any bound refuses identity. This is an event-derived compatibility capability with explicit uncertainty, not general observability for arbitrary old services.

Old and mixed serving release IDs remain distinct from the current release and still fail the unchanged verifier. Recovery still needs the exact approved release plus three fresh matching build/request-echo checks of the original symptom, five seconds apart within the existing60-second/12-probe budget. Verification records the identity source/coverage per round. A passing public endpoint alone is partial evidence when provider identity remains unavailable.

## Serving readiness and one read-only recheck

Provider READY does not start the symptom-verification clock until exact serving identities match. This observation wait is bounded by the original600-second reconciliation deadline. The unchanged verifier then requires three fresh complete original-endpoint/build/request-echo rounds, at least five seconds apart, within60seconds/12probes and the remaining original deadline.

An owner may request `POST /api/operations/{id}/recheck-recovery` once after an inconclusive result for the same submitted operation, within that original reconciliation deadline and unchanged target/release/policy/incident generation. This route has no provider-write path. Every prior attempt remains archived; the current-result pointer updates after atomic publication. Persisted attempt token, state and revision guard worker entry, readiness transitions, generic updates and terminal publication; incident and operation/history commit together. Stale workers neither publish recovery nor overwrite another attempt. Safe raw probe results and the exact policy snapshot remain in each new verification result.


## Historical metrics and rejected-draft diagnostics

The documented CPU/memory history routes were independently checked against the public OpenAPI/current console and actual GET responses on the two enrolled disposable apps. They accept Unix-second `since`; the tested `end` parameter is ignored and is never sent. Each new history read uses a fixed observer cutoff and `since=floor(cutoff-300)`. Every native point is validated; only timestamps at or before that cutoff and no more than300seconds old are eligible. The latest eligible point is selected separately per applet/metric, without replica summing, time shifting, capacity percentages or exhaustion inference. Future/stale/invalid exclusions, missing metrics, partial source errors and display truncation are explicit. Raw provider series remain with immutable evidence for owner audit; the model projection removes all raw series and retains only selected historical observations, provenance and coverage. History is labelled historical even when its evidence age is recent; it does not resolve invalid summary timestamps or independent clock uncertainty. The resource panel uses this separate fallback when summary values cannot be shown, retaining the summary warning. Actual GET and rendered evidence live in historical-metrics-live.json and historical-metrics-ui.json under qa-evidence/.

Authenticated `GET /api/incidents/{id}/rejected-drafts` exposes at most the last8sanitized investigator-validation rejections for that owner's incident, at most8192JSON UTF-8bytes each. It retains a bounded rejected draft and controlled validation reason, never raw validation exception text or credentials. Captures are immutable per run/call and separate from evidence/diagnosis; rejected drafts are never fed to later model calls. Existing external error codes and fail-closed behavior remain unchanged. No rejected draft can be recovered retrospectively for an earlier undetailed failure.

The two-call investigator advertises only currently executable reads. A final call or an exhausted read budget permits conclude only, lists no available reads and reports zero remaining read budget; cautious unresolved/no-change conclusions remain allowed. This fixes a deterministically reproduced budget/schema inconsistency, not an established cause of the original live undetailed rejection. Numeric budgets and freshness/citation gates are unchanged.
